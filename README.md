# CRNA Hub — functional local-first release

This is a static, mobile-friendly application. Deploy it on Vercel using **Framework Preset: Other**, **Root Directory: `./`**, and **Build Command: none**. Upload the *contents* of this folder to the repository root (not the ZIP itself). Vercel should redeploy when `main` is updated.

- Shift management, facility-specific default rates, monthly income totals, shift CSV export
- Hospital profiles with rates, one-way distance, and offline notes
- W-2 PTO hours ledger with balance and accrual rules (manual accrual posting)

## Credentials — connect-first design (manual entry is fallback only)
The intended product is fully integrated credentialing: when the user connects NBCRNA, AANA, and state nursing portals, the app pulls their information automatically, with minimal to no manual entry. The Credentials tab is built that way now — connection cards first, Certification documents directly under the State Licenses card, then a single manual-entry form (type dropdown) below, clearly labeled.
- **NBCRNA card** would pull: certification status, certification period, renewal / recertification deadline, MAC Ed / MAC Dev progress, and CPC check-in status.
- **AANA card** would pull: membership status, membership expiration, and CE transcript totals (Class A / Class B).
- **State Licenses card** would pull, per state: license status, license type (RN / APRN), license number, issue date, and expiration date.
- **Connect buttons do not fake a connection.** The designed path is the finished native app's system sign-in sheet (see "Portal sign-in — final native design" below). **Preview stand-in — the finished app signs you in with the system sign-in sheet:** in this web preview Connect opens the real portal in a new tab for you to sign in yourself, then "I signed in — check it" asks the assistant to read the record page you show it (screenshot or pasted text) and confirm what it saves in a preview. No portal passwords are stored, and no client-side code attempts to scrape a portal.

## Portal sign-in — final native design (spec, Nov 5, 2026)
The finished product is a native iOS App Store app. Portal sign-in in the finished app works like this:
1. **Connect opens the portal in Apple's system sign-in sheet** (`ASWebAuthenticationSession`). The sheet is Apple's UI, not the app's: iPhone Passwords + Face ID fill the login, the user sees the portal's own domain, and CRNA Hub never receives the portal password.
2. **The assistant reads the record page** — status, numbers, dates, CE credits — server-side through the portal-sync Edge Function where a pull is possible, or from the record page the user shows the assistant where it is not — and shows a **preview of exactly what it will save. Nothing is saved until the user checks the preview and approves it.**
3. **A record is labelled Verified only when a pull/check actually returned a record** from the portal (source + retrieval date). Anything else stays user-entered or assistant-portal-check — never upgraded, never faked. A record a server pull already verified is never downgraded by a later assistant check.
4. **Monitoring is an active assistant job:** weekly by default, escalating to every 3 days inside 90 days, every 2 days inside 30 days, daily inside 7 days / once expired. Public checks run automatically; private portals run when the user is signed in, and the assistant prompts the user to sign in again (system sheet) when a check is due and no session exists. It never silently logs in as the user and never stores a portal password. In the web preview checks cannot run in the background while the app is closed — due checks are flagged and run on tap.
5. **The server (portal-sync Edge Function) owns:** the NBCRNA public verification pull (no login), honest blocked/unsupported answers for WV / Ohio lookups with the manual route + Nursys e-Notify pointer, and `portal_connections` status rows. It does **not** own sign-in: the legacy `connect-aana` endpoint (server took a username/password for one AANA attempt) was **deleted Nov 5, 2026 (audit F9)** — the final product never hands the server a portal password, even transiently.

Per-source honest status (Nov 5, 2026 — re-check before claiming more):
- **NBCRNA — unproven.** Public verification submit 404s server-side; member-portal record (MAC Ed / MAC Dev / CPC check-in) needs the signed-in sheet.
- **AANA — likely blocked.** Member sign-in is SSO + Incapsula bot-gated; the sheet is still the correct attempt, and a blocked sheet falls back to the assistant reading the member page.
- **WV Board lookup — blocked** (Imperva Incapsula). **Ohio eLicense — blocked** (Salesforce Lightning app, no public API). Manual route only, plus free Nursys e-Notify for push alerts. Nursys does **not** verify APRN licenses and is never claimed as a pull.

The spec lives in code as `PORTAL_NATIVE_SPEC` in `app.js` (with per-source `finalFlow` copy on each Connect card) and in the header of `supabase/functions/portal-sync/index.ts`. The stand-in label is `PORTAL_STANDIN_LABEL` in `app.js`, rendered in a dashed-amber `.standin` box wherever the preview flow appears.

## Ask Assistant — live server version (built, not yet deployed)
The Assistant is a live AI model via the `assistant-chat` Supabase Edge Function (`supabase/functions/assistant-chat/index.ts`, gpt-4o-mini), not client-side code alone — the deterministic in-app answers remain as the labelled fallback:
- The AI provider API key lives only in the Edge Function's server-side secrets (never in the repo, never in client JavaScript, never in Vercel client env vars). It is the same `OPENAI_API_KEY` secret `extract-contract` uses, set once in the Supabase dashboard.
- The app calls only the Edge Function over HTTPS, authenticated as the signed-in user (Supabase Auth JWT via the same-origin proxy `api/fn.js`), and the function verifies the user server-side.
- The function sends the model only the minimum needed to answer: the user's question plus a small, structured summary of their own records for that question (upcoming shifts, totals) — never facility notes/codes, never documents, and never patient information, and never a document's contents without the user's explicit authorization for that request. The summary shape is allowlisted on both sides; a denied key (notes, codes, passwords, patient info, addresses, emails) rejects the request server-side.
- Rate limiting: client at most one live call per 10 seconds, never more than one in flight; the function enforces a best-effort per-user throttle (1 per 10s, 30 per rolling hour). The durable per-user cap (`assistant_chat_log` table) is final-only and not yet built — see the function's header comment. No clinical advice (the model is instructed to refuse clinical questions); every answer about records must cite the records it used, and say plainly when data is missing.
- Deploy: `supabase functions deploy assistant-chat` (not yet deployed as of Nov 5, 2026). Until it is deployed and the key is set, the Assistant tab falls back to deterministic on-device answers, labelled “On-device answer” — it never pretends a local answer came from the model.

## Supabase Auth + credential sync (new on branch `muse/credentialing`)
The app now signs users in with Supabase Auth (email + password, via the Auth REST API — no extra JS dependency) and syncs credential records to the five migration-001 tables (`nbcrna_profiles`, `aana_memberships`, `licenses`, `ce_records`, `portal_connections`), each row scoped by `user_id = auth.uid()` under Row Level Security. A new **Account** tab shows signed-in state (email, signed-in vs signed-out) and the current mode, which is also shown in the header: cloud, on-device, signed-in-but-undecided, cloud-offline, or "Supabase not configured".
- **What syncs:** NBCRNA, AANA, licenses, CE records, and portal-connection status only. Shifts, facilities, mileage, and PTO stay on-device in this release.
- **No silent overwrites:** on first sign-in the Account tab offers an explicit choice — "Upload my on-device records to my account" or "Load cloud records onto this device" — and nothing syncs until the user picks one. Backups restore onto the device only and never overwrite the cloud account; uploading restored records is a separate, confirmed step on the Account tab. When signed out or offline, the app falls back to its existing localStorage behavior.
- **Connect cards are honest:** on the Credentials tab, signed-in + rows present = "Connected" with the last-synced time; signed-in but no rows = "Connected, no records yet"; signed out = "Not connected". Connect buttons still never fake a portal pull.
- **What still does NOT work:** live NBCRNA / AANA / state portal pulls. The portal-sync Edge Function exists in this repo, but the NBCRNA public verification pull is unproven (submit 404s), AANA sign-in is bot-gated, and WV / Ohio lookups block automation — so no pull is represented as working anywhere in the app.

## Important limitations

Income figures are estimates from your own rates and shifts — always double-check them against your actual paystubs. CRNA Hub is not liable for mistakes. (Shown in the app on the Dashboard near the income totals, on the Facilities/contract preview, and in the onboarding guide's facilities step.)
Credential records are user-entered and are not verified by NBCRNA, AANA, or any state board, even when synced to Supabase — sync moves records between the device and the account; it does not verify them. When Supabase is not configured (or the user is signed out), records are saved to this browser's localStorage and are not synced across devices. Back up regularly. The live AI assistant needs the `assistant-chat` Edge Function deployed and the OpenAI key set; until then it falls back to on-device answers, labelled honestly. There is no OCR for scanned/image-only PDFs or Excel uploads, no automatic driving detection, no alarm scheduling, no push notifications, and no QuickBooks/TurboTax direct integration. CSV exports can be used for manual workflows. Do not store passwords or patient information. Facility codes/notes on a shared device should be treated as sensitive because localStorage is not encrypted. Mileage tax treatment depends on facts; regular commuting is generally nondeductible. Mileage auto-calculation uses public no-key geocoding (OpenStreetMap Nominatim, falling back to Esri ArcGIS World Geocoding) and driving routing (OSRM) only when you ask for a calculation; a distance that cannot be computed is left blank, never guessed, and the draft generator falls back to a facility's manually entered one-way distance.

## Calendar import — all facilities, driven by the Facilities tab

Getting started now runs in this order: 1 Create an account, 2 Add facilities, 3 Sync calendars, 4 Connect credentialing services and licenses, 5 Upload certifications, 6 Upload current contracts. Step 2 checks off when at least one facility exists.

The Facilities tab is the source of truth for calendar import. Each facility has a name, short names / abbreviations (comma-separated, e.g. CAMC), and a pay rule (hourly rate, paid hours for an 8-hour shift, flat rates for 8/10/12-hour shifts and 24-hour call, second-call rate, overnight call bonus). The Apple live-sync import recognises every work shift for those facilities — by name or abbreviation, in the event title or the event location, even an event titled with just the facility name — and prices it from that facility's rule only. Holzer keeps its exact confirmed rates regardless of what the Facilities list says. Shifts for facilities not yet listed do NOT import yet: a facility-like title plus a shift pattern (e.g. "CAMC 8") makes the sync suggest the hospital instead — "We noticed shifts at <Hospital> in your calendar. Add it as a facility?" — with the three paths together: sync your calendar, upload a contract, or manually enter the facility's hourly rate (manual entry is the fallback for rates the other two paths did not provide). Nothing is added without the user's tap; "Not now" dismisses that hospital and the next sync does not re-ask (dismissed suggestions stay visible on the Facilities tab with an "Ask again" button). Adding a facility also re-scans events that were held before it existed, and the next sync imports them, priced. The import reads the full source-calendar history (past dates included) and dedupes by date + facility + shift type, alias-aware, so a shift first imported under an abbreviation is not re-created under the full name. Unpriced shifts are counted in the totals as unpriced, never folded in as $0. Facilities live on-device, like shifts — the server stores none of them and no new migration is needed; the browser sends the list with every sync.

## Final native calendar sync (EventKit) — design

The finished product is a native iOS App Store app. This section is the design the sync panel already describes and the native build must implement. The web preview implements the same flow except for the Apple transport, which is a labelled preview stand-in (see below) — nothing else in the panel is a stand-in.

**The user flow (final):**
1. The user connects once per provider and picks which *existing* calendar is their work calendar (for example "Caleb Work Schedule"). The app pulls shifts from that calendar only — no other calendar is ever read.
2. The app creates its *own* calendar behind the scenes, for the shifts the user adds in CRNA Hub. The user never creates a calendar, never labels anything "CRNA Hub", and never manages the app-owned calendar. The work calendar is never written to.
3. Google/Outlook connect with one click through their OAuth consent screens. Apple connects with one tap: grant calendar access, pick the work calendar. No password is ever typed, for any provider.

**What the native layer must do (Apple / EventKit):**
- Request calendar access (`EKEventStore requestFullAccessToEvents`) once, at connect time; if the user denies it, say so plainly and offer the .ics import instead — never fake a connection.
- Show the system calendar picker (`EKCalendarChooser`, selection style single) so the user picks their existing work calendar; store only that calendar's `calendarIdentifier` (in the keychain / app group, never in a backup-visible note).
- Create the app-owned calendar on-device (`EKCalendar`, `EKSource` local/CalDAV as appropriate, title internal only — the user never sees or edits this name) and write CRNA Hub shifts there only.
- Observe changes (`EKEventStoreChangedNotification` + background fetch while the app runs) and re-run the same sync rules as the preview: facilities-driven parsing, dedupe, proposed status, unpriced-never-$0, ask-first hospital suggestions, newest-wins, pending deletions. The parser and rules in `supabase/functions/_shared/calendar.ts` are the reference implementation — port them, do not re-invent them.
- Never write to the work calendar, never delete from it, never move events out of it. An event that disappears from the work calendar is never treated as a deletion on its own (a full scan cannot see deletions); deletions of CRNA Hub shifts are confirmed by the user first (Pending deletions), exactly as in the preview.

**What the server still owns (sync-calendar Edge Function):**
- Google/Outlook OAuth token exchange and refresh, token storage (encrypted, server-side only), and the Google sync-token / Outlook delta-link machinery.
- The sync engine: `calendar_sync_map` pairing (shift id ↔ provider event id, last-seen timestamps both sides), `calendar_import_map` pairing for work-calendar imports (migration 004; delivery flags in migration 005 so a shift lost to an interrupted sync is repaired, never skipped forever as if deleted), the sync log, and pending-deletion bookkeeping.
- The facilities-driven shift parser (`parseWorkShiftEvent`), the ask-first hospital-suggestion flow, and the skip-reason counts (`skippedNotShift` / `skippedDeleted` / `skippedLegacy` / `skippedSuggested`).

**What moves on-device (native):**
- The entire Apple transport: EventKit replaces CalDAV, the app-specific password, and the server-side Apple credential entirely. The native app never sends an Apple password anywhere.
- Later, once shifts live in a cloud table (they are on-device only in this release), the parser, dedupe, and suggestion flow can move on-device too and the sync-calendar function shrinks to Google/Outlook transport only. That move is a separate step — it must not change any sync rule.

**Preview stand-in (web preview only — not the final flow):**
- Apple connects through CalDAV with a one-time app-specific password, and the app-owned calendar is created server-side through CalDAV. In the UI this is fenced off in a dashed-amber "Preview stand-in" box (`LIVE_SYNC_STANDIN_LABEL` in `live-sync.js`, `.preview-standin` in `styles.css`) that says plainly: "Preview stand-in — the finished app uses EventKit, no password needed". The password field is cleared immediately after sending, the value is never stored on the device, and every alert the stand-in path shows carries the same label.
- The work-calendar picker itself is *not* a stand-in: picking the existing calendar and pulling from that calendar only is the final flow, and it works the same way in the preview.

**Rules that never change, preview or final (regression checklist — see `test-calendar-sync-final.js`):**
- Facilities drive recognition and pricing; a shift at an unknown hospital is held and suggested once, never imported, never auto-created; "Not now" dismisses it and the next sync does not re-ask.
- Dedupe via `calendar_import_map` (plus the local date+facility+type guard); a shift the user deleted is never re-imported; a stale import row (shift paired but never delivered) is repaired, not skipped forever.
- Imported shifts arrive as `proposed`, never auto-confirmed; a shift with no pay rule stays unpriced (pay blank, `incomplete`) — never $0 — and is excluded from income totals.
- Newest edit wins; deletions wait in Pending deletions unless auto-delete was explicitly turned on (default off); a user-confirmed local deletion is sent as a tombstone and applied to the provider.

**Still to build (server-side, before the native flow is complete for Google/Outlook):** a work-calendar picker for Google and Outlook matching Apple's — today only Apple has one (`set-apple-source-calendar`); Google/Outlook still sync only to the app-owned calendar. The panel copy for Google/Outlook already describes the final flow, but the picker itself must land before the copy is fully true for those providers.

## Facility rates are optional — blank means "not taken here", never $0

Every rate field on the facility form (hourly, 8h, 10h, 12h, 24h call, second call, overnight call bonus) is optional. Leave a rate blank when it does not apply at that hospital — for example, no 24-hour call rate at a hospital where you do not take call. A blank rate never blocks saving, and a shift type with no rate stays unpriced/incomplete and flagged — it is never priced at $0 and never folded into income totals as $0. A 0 entered in a rate field is treated as blank when saved, and any 0 already stored is normalised to blank when the app loads (or when a backup is restored). The facilities list shows only rates that are set; unset call types are labelled "Not taken here".

## Mileage from home — or from a hotel stay

Save a home address once on the Account tab (also shown on the Mileage tab) and mileage auto-calculates as the driving distance from home to each facility's saved address — round trip by default, or one way if you choose that mileage type (per-user default on the Mileage tab, changeable per trip; a round-trip trip is counted once in totals, never doubled), using public no-key services the web preview can reach: OpenStreetMap Nominatim (falling back to Esri ArcGIS World Geocoding, which covers newer US street addresses Nominatim misses) for geocoding and OSRM for driving distance. If either address cannot be located or the route cannot be computed, the mileage is left blank for manual entry — no distance is ever invented or estimated from a straight line. Auto-calculated mileage is labelled as such, stays editable per trip (editing marks it as your override), and, once confirmed in the weekly review, feeds the mileage totals and CSV export like manual entries (unconfirmed drafts count in neither). The facility form can also calculate and save its one-way distance from home.

Staying in a hotel for a block of shifts: add a hotel stay on the Mileage tab (hotel address + check-in/check-out dates, optionally one facility) and mileage drafts for shifts in that block are calculated from the HOTEL address instead of home. When logging a trip by hand, pick "Hotel" as the starting point and enter the hotel address — it is remembered (and offered from previously used addresses) so you do not re-type it for every shift in the block. Every trip record shows whether it is home-based, hotel-based, or from another address, with the address, and the CSV export carries both. If no hotel address is given, mileage defaults to home-based.

## Weekly mileage review

One screen per week (Mon–Sun) on the Mileage tab to confirm all trips at once — no daily confirm. Opening the week auto-drafts a trip for every shift in it: origin guessed home by default, or the hotel address when a saved hotel stay covers that shift date, with auto-calculated miles (round trip by default, per the mileage type). A trip whose distance cannot be computed is drafted with blank miles and flagged for manual entry — never guessed. Each row shows the date, facility, origin (Home / Hotel / other address), miles with a round-trip/one-way label, and controls to change the origin, edit the miles, or skip the trip. A single "Confirm all" button confirms the whole week; confirmed trips move from draft to verified and count in mileage totals and exports, unconfirmed drafts do not. A trip confirmed with a changed origin keeps that origin for that trip only — no hard rule is created. The review is due on Sunday, at the end of the week just ended: the Dashboard shows a nudge ("Week of Nov 2–8: 5 trips to review" / "All confirmed") when a week's review is due or overdue, linking to the review screen. Past weeks stay reviewable until confirmed.

Reads and migrates records from `crna-hub-starter-v1` without deleting the original. Restore from JSON if moving devices. Browser private mode, site data deletion, or browser changes can erase local records.


## Contract pictures (OCR)
Pictures of contracts (.png, .jpg, .jpeg, .webp; .heic only where the browser can decode it) are read entirely on the device with Tesseract.js, loaded from a CDN only when a picture is chosen — no picture is sent to a server for OCR, and no AI model reads it. OCR text goes through the same deterministic parser and the same preview/approval flow as text contracts, with every row flagged "from photo — check carefully" because OCR can misread digits and dates. Approved pictures are stored in IndexedDB on that device (not localStorage) and viewable from the Saved contracts list; cloud document storage is not enabled yet, so pictures do not sync to Supabase in this release.

## Certification documents (ACLS / BLS / PALS / NRP) — migration 002

On the Credentials tab, directly under the State Licenses connection card, the "Certification documents" section accepts ACLS, BLS, PALS, NRP, and Other certifications, each with a file upload, issue date, and expiration date, plus Download / Replace / Delete controls.

How expiration dates work: when a text file or text-layer PDF states an expiration / valid-through date, the app reads that date from the document and stores it with source "extracted" — the user can correct it in the form at any time. Images cannot be read for a date, and a document stating no expiration is marked "no expiration found": in both cases the user enters the date manually. Dates are never invented. Expiring certifications surface on the Dashboard under Credential deadlines on the same 90/60/30/7-day windows as licenses, labeled by source (extracted vs manually entered).

Cloud storage setup (owner step, dashboard/SQL only — no secret key anywhere):
1. Run `supabase-schema-002.sql` (in the project files, alongside migration 001) in Supabase SQL Editor. It creates the `public.documents` metadata table with Row Level Security (own-rows only) AND creates the private `certification-documents` Storage bucket with per-user policies: each user can only upload, download, update, or delete objects whose first path segment is their own user id.
2. Until that SQL has run, the app says so plainly: signed-out users see "Sign in and enable document storage to upload files", and signed-in users whose upload fails see the storage error — in both cases file details are saved on this device only and the file itself is not stored. Files are never served from a public URL; downloads come from the user's own storage path with their auth token.

What still does not work: live NBCRNA / AANA / state portal pulls (the portal-sync Edge Function exists in this repo, but NBCRNA verification is unproven — submit 404s — AANA sign-in is bot-gated, and WV / Ohio lookups block automation), and live AI extraction. Document records are user-entered / document-extracted, not verified by any board. Contract-picture OCR exists (see Contract pictures above); it does not read certification-document expiration dates from images.
